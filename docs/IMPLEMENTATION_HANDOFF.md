# Implementation Handoff

## 상태와 목표

이 저장소는 설계 문서만 있습니다. 기존 SDK·빌드·샘플·테스트가 구현되어 있다고 가정하지 마세요. 설치 좌표와 공개 API도 확정 전입니다.

구현 목표는 두 가지입니다.

1. STG에서 shake → 원래 화면 캡처 → 주석·가림 → 검토 → 앱 안에서 기존 Jira 티켓에 첨부.
2. 호스트 프런트엔드가 이미 사용하는 소수의 로컬 상태 값을 읽고 변경·초기화하는 간단한 Developer mode.

로컬 파일 내보내기는 개발 PoC일 뿐 사용자용 Jira MVP의 대체가 아닙니다. 서버 관리자 액션, 상시 녹화, 임의 스크립트 실행은 범위 밖입니다.

## 로컬 Developer mode의 엄격한 범위

개발자 모드 MVP에서는 API 호출을 통한 서버 플래그·데이터 변경을 제외합니다. Jira 보고서 업로드는 별도 기능입니다. 로컬 값이라도 인증·토큰·계정 상태이거나 변경이 서버 동작을 유발할 수 있으면 토글 대상에서 제외하고, 필요한 경우 민감값을 가린 읽기 전용 표시만 검토합니다. 실제 저장소가 어떤 정보를 관리하는지 목록화하는 작업이 먼저이며, 실제 호스트 키·타입·용도는 아직 확인하지 않았습니다.

서버 상태 변경 기능은 후속 자동 구현 대상으로도 잡지 마세요. 새로운 요청과 별도 검토·승인이 필요합니다. 저장소 분석 결과부터 제시하고 안전성이 확인된 비민감 로컬 항목만 제어하세요.

## 먼저 확인할 입력

- 호스트 Android 저장소와 STG/release 변형 구조, 최소 Android 버전
- 호스트 프런트엔드 저장소, WebView 생성·탐색·브리지와 페이지 준비 신호
- 실제 storage 키·저장소 종류·직렬화 타입·기본값·소비 시점·초기화 의미
- STG origin 목록과 안전한 화면 식별자
- Jira Cloud/Data Center, 인증 경로·게이트웨이 운영 주체·권한
- 파일 TTL·크기 한도·검증 기기와 비민감 테스트 자료

이 정보는 아직 검증되지 않았습니다. 접근할 수 없는 코드·키·환경은 추측하지 말고 필요한 입력으로 보고하세요. 회사 전용 키·화면·로그·자격 증명을 공개 저장소에 넣지 마세요.

## 권장 구현 순서

### 1. 가장 작은 구조와 variant 분리

기존 코드가 있다면 먼저 읽고 해당 빌드·테스트 규칙을 따르세요. 없다면 Android 최소 모듈과 비민감 샘플부터 제안하세요. STG 실제 구현과 release/no-op 경계를 먼저 만들고, 아직 필요 없는 모듈·플러그인·범용 설정 엔진은 늘리지 마세요.

### 2. 실제 프런트엔드 저장소 분석

read/write/remove 호출과 해당 값을 소비하는 코드를 함께 추적하세요. 키가 있다는 사실만으로 QA 제어 항목으로 등록하지 마세요. 타입, 없을 때의 동작, 문자열 직렬화, 메모리 캐시, origin/session 범위와 변경 후 재로딩 필요를 확인하세요.

먼저 소수의 비민감 항목만 고릅니다. 실제 키를 두 번째 Eora 저장소에 복사해 이중 관리하지 않습니다. 호스트의 기존 값이 기준입니다. boolean에는 on/off만 제공합니다. 다른 타입은 읽기 전용 또는 호스트가 정한 제한된 버튼 콜백으로 처리하거나 MVP에서 제외합니다. 범용 값 편집기·앱별 도메인 프레임워크는 만들지 않습니다.

### 3. 호스트 등록 콜백과 Developer mode

선택적 개발자 확장에서 호스트가 라벨·키·읽기·쓰기·초기화를 소유하고 Eora는 기본 버튼·Boolean 토글·현재값·확인·결과만 표시하도록 구성하세요. 캡처·주석·제보 코어에 호스트별 기능을 넣지 마세요. 초기화의 의미는 키 삭제(unset)와 기본값 복원을 구분합니다. false와 unset을 혼동하지 마세요.

STG origin·키 허용 목록, 현재 WebView·페이지 준비·탐색 세션 확인을 적용하세요. 페이지 전환 후 늦게 온 콜백은 무시합니다. 작업 후 재조회로 반영 여부를 확인하고, 새로고침·재진입이 필요하면 안내합니다. 입력 손실을 일으킬 새로고침은 사용자 확인 후 실행합니다.

localStorage, sessionStorage, 쿠키, 캐시를 구분하세요. 전체 쿠키·캐시 삭제·전체 로그아웃은 첫 로컬 MVP에 넣지 마세요. 임의 키 입력, JavaScript 편집기, 웹 페이지가 호출할 수 있는 범용 관리 브리지는 제공하지 마세요.

### 4. Shake와 증거 초안

foreground의 활성 화면에서만 shake를 감지하고, 감도·쿨다운·중복 방지와 수동 트리거를 제공하세요. 원래 화면을 먼저 캡처한 뒤 제보 UI를 여세요. lifecycle 변화나 화면 전환으로 캡처 대상이 달라지면 취소하세요. 원·화살표·텍스트·불투명 가림을 합성한 최종 파일만 검토·전송 대상으로 만드세요.

Dari는 필수 의존성이 아닙니다. 함께 쓰는 호스트라면 desktop-only 설정과 shake 충돌 여부를 확인하되 다른 도구의 설정을 자동 변경하지 마세요.

### 5. Jira 직접 첨부

인증 방식이 결정되기 전에는 가짜 API나 APK 내 secret으로 빈칸을 메우지 마세요. 승인된 게이트웨이 또는 기존 서버 경계에서 호출자·티켓 권한과 비밀 관리를 구현합니다. 서버리스도 이 책임이 사라지지 않습니다.

대상 티켓과 최종 파일을 확인받은 후 첨부를 추가합니다. 기존 첨부의 upsert/교체를 가정하지 마세요. 보고서 ID·revision·파일별 결과를 관리하고 부분 성공 및 응답 유실을 구분하세요. 불확실하면 자동 재전송하지 말고 상태 확인을 요구하세요. 온라인 복구만으로 자동 전송하지 않습니다.

### 6. 검증 후 범위 확대

기존 영상 선택을 먼저 검증하고 앱 내 MediaProjection 녹화는 이후에 추가합니다. 서버 관리자 액션과 봇 서버 재사용도 실제 수요·승인된 경계가 확인된 뒤 별도로 진행합니다.

## 완료를 판정할 테스트

- 등록한 실제 키의 현재값·타입·허용값·on/off·reset/unset이 프런트엔드 동작과 일치한다.
- 알 수 없는 키/origin, 민감 항목, 준비 안 된 페이지에서는 실행하지 않는다.
- navigation 중 작업과 늦은 콜백이 다른 페이지의 상태를 바꾸지 않는다.
- 새로고침 없이 반영되는 경우와 재진입이 필요한 경우를 구분해 표시한다.
- 연속 shake·회전·background 전환·센서 부재·수동 진입에서 제보가 중복되지 않는다.
- 캡처에 제보 UI가 섞이지 않고 가림 전 이미지가 전송되지 않는다.
- View·Compose·WebView 및 사용 중인 별도 Window/Surface를 실제 기기로 확인한다.
- Jira 권한 오류·크기 제한·부분 성공·응답 유실·재시도에서 거짓 성공이나 중복 첨부를 만들지 않는다.
- 취소·TTL·용량 부족 시 임시 파일과 상태를 안전하게 정리한다.
- release/no-op에는 QA 센서 구독·화면·관리 액션·업로더·추가 권한이 유입되지 않는다.

테스트 결과는 통과·실패·미실행으로 나눠 보고하세요. 문서만 수정한 상태를 작동하는 SDK로 표현하지 마세요.
